# Community photos and independent trip copies

Apply `sql/community-imports.sql` once to the existing Supabase project, after the Week 6 Community and Phase 3 migrations. Do not re-run the original migrations. This adds private provenance metadata, an authenticated atomic import RPC and a deferred adoption trigger; it does not rewrite original trips or widen their permissions.

Community cards/details and My trips cards now use the same destination slideshow as trip details: up to five current attributed Google Places images, lazy loading, five-second rotation, pause/play, navigation/swipe, offscreen/hidden-tab pause and reduced-motion support. Multi-stop destinations rotate across stops; unavailable photos use the existing illustration. Community images can only be read for published snapshots, with all Google credentials retained on the server.

From a Community detail, **Save to My trips** asks for a start date and copies the public title, destination and activities into a new, private trip owned by the requesting account. The end date follows the snapshot's day count. It copies no source members, dates, preferences, votes, requests, model prompts or responses. Activity IDs are new and positions normalize to zero per day. Repeated saves of the same publication by the same account open the existing copy; deleting the copied trip permits saving a new copy later. A successful import is one transaction, including metadata, version and items.

The card initially reads **Shared by [author]**, but the downloader already has owner permissions: manual itinerary editing, personal/group preferences, invitations, AI day/activity revisions and whole-trip regeneration through the normal preview/apply flow. An imported plan has no AI preference baseline; its owner can establish one by regenerating. Generating an AI proposal alone never changes the badge.

After an actual changed version is committed, a deferred trigger changes the card to **Owned**. It compares complete activity content against the imported version, so opening the editor, previewing AI output, cancelling, failing or saving an identical plan does not adopt. The source attribution is retained permanently in metadata and the trip detail. Once adopted, reverting content does not remove the Owned status. Withdrawal or deletion of the original publication does not delete the independent copy. Existing member-shared trips retain their original permission semantics and labels.

Run `npm run test:community`, `node scripts/verify-travelers.mjs`, `node scripts/verify-destination-photos.mjs`, `npm run test:phase3`, `npm run test:week6`, lint and production build. The isolated PostgreSQL tests cover private ownership, idempotence, atomic rollback, public-only copies, normalized activity order, preview/no-op/rollback stability, adoption and source deletion. API tests cover session ownership, origin/date/body validation, large bigint IDs and public multi-destination photo access.

Live acceptance: open Community with two accounts; save a publication with a chosen date, confirm the new private trip appears as Shared by the author, edit and save one activity, then refresh My trips and confirm Owned. Verify the original publication and original owner's trip remain unchanged. Test no-op/cancel/AI preview before adoption, duplicate save, withdrawal of the source, and slideshow pause/swipe/reduced-motion on desktop/mobile. Test account-created copies are real private trips: keep or delete them explicitly after review.
