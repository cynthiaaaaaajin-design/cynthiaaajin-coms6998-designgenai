# TripSync 3 architecture and decision rules

Audited the current Public repository, the previous TripSync 2 release evidence, and the unchanged Studio/Admin integration. Existing `trip_preferences` is member-editable and shared only with current trip participants. Existing activity likes/dislikes and the “Group consensus” review-completion card do not vote on alternative plans. Existing immutable `itinerary_proposals`, scoped merge/apply RPCs, preference/reservation snapshots, trip-row locks and `studio_trip_runs` already provide the generation and publication machinery to reuse.

TripSync 2 is deployed with persistent chat, reservations and deterministic expenses; supplier inventory is an external-link fallback. Its dedicated multi-account and full mobile touch tests remain limited. This release will regression-test those capabilities rather than assume a feature name proves it works.

Checkpoint: `/private/tmp/tripsync3-before.bundle`, original tracked diff in `docs/checkpoints/tripsync3/public.patch`, original untracked archive `/private/tmp/tripsync3-untracked-before.tar.gz`, and HEAD/status manifests for all three repositories. Existing user files remain untouched. Only Public and additive shared SQL need changes; no published chains or unrelated projects are changed.

Preferences gain explicit activity priorities, dietary/transport lists and an optional availability date window. All submitted fields are visibly disclosed as shared with current trip members and used for planning. Existing must-visit/interests/hard-constraint/budget/pace fields remain authoritative. New fields have empty defaults; older submissions remain valid. Expanded snapshots safely invalidate pre-upgrade pending proposals; no old version or rating is changed.

Conflict rules use explicit structured evidence. Must-have versus cannot-accept for the same activity is a hard issue; distinct budget limits and relaxed versus packed pace are ordinary differences, not proof of infeasibility. Different currencies/scopes are never averaged. Nonoverlapping availability is a hard scheduling issue. Free-text AI interpretation must quote real stored fields from distinct members and is labeled as a suggestion requiring human review, not a proven disagreement.

Decision rounds freeze the electorate, preference snapshot, trip/reservation context and exact parent itinerary. Defaults: unanimous support for one candidate; optional strict majority of the whole electorate (floor(N/2)+1), not only votes cast. Votes are visible to current members, may be changed before the explicitly configured deadline, and are unique per member/round. Abstaining or missing submissions do not count as approval. A tie or expired round below threshold has no winner. Membership/preference/reservation/trip/version changes make the round stale and require a fresh round. One-person testing is clearly labeled solo; it is never presented as distinct group participation.

Two or three candidate instructions each use the existing published regional proposal engine independently. Actual generated structured data supplies comparisons and uncertainties; no preview is fabricated. Generation never publishes a version. A round opens for voting only after every candidate has a persisted, schema-valid proposal and an explicit initiator/owner review of constraints and uncertainties. A hard constraint remains binding regardless of majority votes: proposals must disclose accommodations and unresolved conflicts; people review actual before/after and uncertainties.

Publication is owner-confirmed and database-enforced. Linking an existing proposal to a decision round makes ordinary apply paths respect the same electorate/snapshot/threshold/winner checks, so an owner cannot bypass a pending vote by using the older proposal endpoint. Applied decision history freezes the winning proposal, votes, preference evidence, parent/new version and existing exact chain/run attribution.

Availability conflicts that cannot fit the saved trip dates block itinerary alternative generation. The app reports the date issue instead of inventing feasible schedules; members must resolve dates/availability first.
